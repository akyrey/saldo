# Saldo architecture

Saldo is a self-hosted personal finance server for one household, built to replace Firefly III. This document is the contract every phase works against. Changing it needs the owner's approval; record the change in `docs/STATUS.md`.

Contents: [1 Goals](#1-goals) · [2 Decisions](#2-decisions) · [3 Crates](#3-crates) · [4 Domain model](#4-domain-model) · [5 SQL schema](#5-sql-schema) · [6 API](#6-api) · [7 Auth and household](#7-auth-and-household) · [8 Events, webhooks, notifications](#8-events-webhooks-notifications) · [9 Importer and export](#9-importer-and-export) · [10 Frontend](#10-frontend) · [11 Deployment](#11-deployment) · [12 Testing](#12-testing)

## 1. Goals

- Firefly III core features: asset, expense, revenue and liability accounts, transactions, categories, tags, budgets, bills, piggy banks, recurring transactions, rules, reports.
- Four things Firefly III lacks:
  1. Split transactions where every split has its own source and destination account.
  2. Bill reminders: one a few days before the due date, then repeated until the bill is paid.
  3. Webhooks for every domain event, with retries and HMAC signatures.
  4. A household: several users, each with their own accounts, and a combined view.
- No lock-in: an idempotent importer from Firefly III, and JSON/CSV export from the first usable version.
- One server, three clients (web, desktop, mobile). Always online; no offline sync.

## 2. Decisions

| Topic | Decision | Why |
|---|---|---|
| Name | Saldo: crates `saldo-*`, binaries `saldo` and `saldo-import`, headers `X-Saldo-*`, env vars `SALDO_*` | |
| Language, runtime | Rust, Tokio, Axum | |
| Database | SQLite only, through SQLx with compile-time checked queries | One file to back up, one container; household scale |
| Money | `i64` minor units + ISO currency code, never floats | Exact arithmetic |
| IDs | UUIDv7 stored as TEXT | Sortable by creation time like ULID, but an IETF standard (RFC 9562) supported directly by `uuid`, SQLx, utoipa and OpenAPI `format: uuid` |
| Dates | A split has a calendar `date` (`YYYY-MM-DD`). Audit timestamps are UTC RFC 3339 (`2026-11-11T20:21:00.000Z`) | Finance is date-based; no timezone maths in SQL |
| Currencies | One primary currency per household, optional foreign amount per split, no exchange-rate table in v1 | Owner uses one currency with rare foreign purchases |
| Household visibility | Every member sees and edits everything; accounts have an owner for mine / member / household filters | Owner's choice |
| Auth | Password (Argon2id) + server-side sessions + personal access tokens; OIDC later | |
| API | REST under `/api/v1`, OpenAPI generated by utoipa | Typed clients for any frontend |
| Event log | Appended in the same DB transaction as every change, starting in Phase 2 | Outbox pattern; it is an audit log, not event sourcing |
| Import identity | `external_refs` mapping table | Firefly splits have their own user-facing `external_id`, which is kept separately |
| Frontend | React + TypeScript SPA (Vite), PWA for mobile, Tauri 2 for desktop | See section 10 |
| Notifications | ntfy/Gotify, SMTP email, Web Push, and webhooks | |
| Deployment | One Docker image + docker-compose, data in one volume | |

## 3. Crates

```
Cargo.toml                 workspace, shared dependency versions and lints
crates/core/               saldo-core      pure domain: no I/O, no async, no SQL
crates/app/                saldo-app       services (use cases), SQLx repositories, migrations/, response views
crates/server/             saldo-server    binary `saldo`: Axum API, auth, OpenAPI, background workers, embedded SPA
crates/importer/           saldo-importer  binary `saldo-import`: Firefly III API client and mapping
web/                       React SPA (Phase 4), TS client generated from openapi.json
desktop/                   Tauri 2 shell around web/ (Phase 7)
docs/                      this file, PLAN.md, STATUS.md, phases/
```

Dependency direction: `core` ← `app` ← `server`, and `core` ← `app` ← `importer`. Nothing depends on `server`.

Laravel analogy: `core` is plain value objects and domain rules with no framework; `app` is Eloquent models, service classes and migrations; `server` is routes, controllers, middleware and queue workers; `importer` is an artisan command. Go analogy: `core` is a package importing only the standard library; `app` is the package holding `*sql.DB` code; `server` and `importer` are two `cmd/` binaries.

Why `saldo-app` exists: the server and the importer both go through the same services, so imported data passes the same validation and writes the same events as API calls, without the importer speaking HTTP or duplicating SQL.

Rules for all crates:

- `saldo-core` has no dependency that does I/O. Allowed: `uuid`, `chrono` (no `clock` feature), `serde`, `serde_json` (only for the free-form `SplitMeta` object), `thiserror`.
- The current time and new IDs come from outside `core` (parameters or the `Clock` trait in `app`), so tests are deterministic.
- Add dependencies with `cargo add`, so versions are current; shared ones go in `[workspace.dependencies]`.
- `unsafe` is forbidden (`#![forbid(unsafe_code)]`); `unwrap()` and `expect()` only in tests.

## 4. Domain model

This is the shape of the Rust types in `saldo-core`. Names and invariants are binding; field order and derive lists are not.

```rust
// Newtype IDs: a struct wrapping one value, so an AccountId can never be passed
// where a SplitId is expected. (PHP/Go: like `type AccountID string` in Go, but
// the compiler refuses implicit conversion.)
pub struct AccountId(pub Uuid);       // same pattern: HouseholdId, UserId, GroupId,
                                      // SplitId, CategoryId, TagId, BudgetId, BillId, ...

pub struct CurrencyCode(/* 3 uppercase ASCII letters */);
pub struct Currency { code: CurrencyCode, decimal_places: u8 }   // private; Currency::new checks 0..=8

pub struct Money { minor: i64, currency: CurrencyCode }
// Money::parse_decimal("123.45", &eur) -> Ok(12345); "1.234" with 2 places -> Err
// checked_add / checked_sub return Err on overflow or currency mismatch
// to_decimal_string(&eur) -> "123.45"

pub enum AccountType {
    Asset,
    Expense,
    Revenue,
    Liability,
    Equity(EquityRole),               // system accounts, one of each per household
}
pub enum EquityRole { OpeningBalance, Reconciliation }

pub struct Account {
    pub id: AccountId,
    pub household_id: HouseholdId,
    pub owner: Option<UserId>,        // None = joint
    pub name: String,
    pub account_type: AccountType,    // immutable after creation
    pub currency: CurrencyCode,
    pub active: bool,
    // asset role, liability details, iban, ... see the accounts table
}

pub enum SplitKind { Withdrawal, Deposit, Transfer, OpeningBalance, Reconciliation }

pub struct NewSplit {                 // input, not yet validated
    pub date: NaiveDate,
    pub description: String,
    pub source: AccountId,
    pub destination: AccountId,
    pub amount: Money,                // always > 0, flows source -> destination
    pub foreign_amount: Option<Money>,
    pub category: Option<CategoryId>,
    pub budget: Option<BudgetId>,
    pub bill: Option<BillId>,
    pub tags: Vec<TagId>,
    pub reconciled: bool,
    pub notes: Option<String>,
    pub meta: SplitMeta,              // free-form extra fields (SEPA, extra dates, references)
}
pub struct NewTransactionGroup { pub title: Option<String>, pub splits: Vec<NewSplit> }

// Validation turns input into a type that can only exist if it is valid
// ("parse, don't validate"). Services accept only ValidatedGroup.
pub fn validate_group(
    input: NewTransactionGroup,
    accounts: &AccountLookup,         // the accounts referenced, loaded by the caller
) -> Result<ValidatedGroup, Vec<ValidationError>>;

// What validation needs from the database, loaded by the caller: the household,
// the referenced accounts, and the category/budget/bill/tag IDs that exist in that
// household. Anything missing from the lookup counts as unknown.
pub struct AccountLookup { /* private */ }
// AccountLookup::new(household_id).with_account(a).with_category(id).with_tag(id)...

// Balances: two deltas per split (source -amount, destination +amount, or the
// foreign amount for an account in the foreign currency), folded into a map.
pub fn balance_deltas(group: &ValidatedGroup, accounts: &AccountLookup) -> Vec<(AccountId, Money)>;
pub fn apply_deltas(balances: BTreeMap<AccountId, Money>, deltas: &[(AccountId, Money)])
    -> Result<BTreeMap<AccountId, Money>, MoneyError>;
```

`ValidationError` has one variant per broken rule; each split-level variant carries the zero-based `split` index, and `code()` returns a stable string: `empty_group`, `amount_not_positive`, `same_account`, `unknown_account`, `account_outside_household`, `unknown_reference` (category, budget, bill or tag), `invalid_account_pair`, `account_inactive`, `currency_mismatch`, `foreign_amount_not_positive`, `foreign_currency_same_as_amount`, `foreign_amount_required`, `foreign_currency_mismatch`. Its JSON form is `{"code": "...", "split": 0, ...}`.

### 4.1 Split kind

Derived from the two account types and stored on the split. Account type never changes, so the stored value never goes stale.

| Source | Destination | Kind |
|---|---|---|
| Asset, Liability | Expense | Withdrawal |
| Revenue | Asset, Liability | Deposit |
| Asset, Liability | Asset, Liability | Transfer |
| Equity(OpeningBalance) | Asset, Liability (or the reverse) | OpeningBalance |
| Equity(Reconciliation) | Asset, Liability (or the reverse) | Reconciliation |
| anything else | | `ValidationError::InvalidAccountPair` |

A refund is a Deposit from a Revenue account, as in Firefly III.

`SplitKind::derive(source: AccountType, destination: AccountType) -> Result<SplitKind, InvalidAccountPair>`, where `InvalidAccountPair { source, destination }` holds the two types; `validate_group` turns it into `ValidationError::InvalidAccountPair` with the split index.

### 4.2 Ledger invariants

All enforced in `saldo-core`, unit-tested and property-tested; the ones marked (DB) are also SQL constraints.

1. A group has at least one split.
2. `amount > 0` (DB).
3. `source != destination` (DB).
4. The account pair gives a valid kind (4.1).
5. All accounts, categories, budgets, bills and tags belong to the group's household (DB for accounts).
6. Split currency: for Withdrawal and Deposit, the currency of the Asset/Liability side; for Transfer, the currency of the source; for OpeningBalance and Reconciliation, the currency of the Asset/Liability side.
7. `foreign_amount` is `> 0` and in a different currency than `amount` (DB). A Transfer between accounts with different currencies must have a foreign amount in the destination's currency.
8. Both accounts are active when a split is created (editing old splits on archived accounts is allowed).
9. Splits in one group may have different sources, destinations, kinds and dates.

Balance of an account = sum of amounts where it is the destination − sum where it is the source (using the foreign amount when the account's currency is the split's foreign currency). Every split moves money from one account to another, so the ledger is double-entry by construction and the sum of all balances is always zero per currency. Sign convention: Asset positive = you have money; Liability negative = you owe; Expense positive = spent; Revenue negative = earned.

### 4.3 Other domain logic in `core`

- **Schedules**: `fn occurrences(schedule: &Schedule, from: NaiveDate, to: NaiveDate) -> Vec<NaiveDate>` for bills (weekly, monthly, quarterly, half-year, yearly, with `skip`) and recurrences (daily, weekly, monthly, nth weekday, yearly, with `skip` and a weekend policy). Month-end is clamped (31st → 30th/28th). Pure functions; today's date is a parameter.
- **Rules**: `Trigger` and `Action` are enums whose variants carry data, for example `Trigger::DescriptionContains(String)`, `Trigger::AmountMoreThan(i64)`, `Action::SetCategory(CategoryId)`, `Action::LinkToBill(BillId)`. `fn evaluate(rule: &Rule, split: &SplitView) -> Vec<Action>` is pure; applying the actions is a service in `app`.
- **Bill reminders**: `fn reminder_due(period: &BillPeriod, bill: &Bill, today: NaiveDate) -> Option<ReminderKind>` decides `DueSoon` / `Overdue` / nothing.
- **Budget maths**: spent per budget limit, available amount, auto-budget rollover.

## 5. SQL schema

SQLite with `STRICT` tables. Connection settings, applied by `saldo-app` on every connection: `foreign_keys = ON`, `journal_mode = WAL`, `busy_timeout = 5000`, `synchronous = NORMAL`.

Conventions:

- `id` is a UUIDv7 as lowercase hyphenated TEXT. Amounts are INTEGER minor units with a `currency_code`. Booleans are INTEGER 0/1. Dates are `YYYY-MM-DD`; timestamps are UTC RFC 3339 with milliseconds and `Z`, so text ordering is time ordering.
- Every domain table has `household_id`. Tables referenced by NOT NULL foreign keys have `UNIQUE (household_id, id)` so the reference can be a composite key, which makes cross-household references impossible at the database level. Nullable references use a single-column key with `ON DELETE SET NULL` (SQLite cannot null only one column of a composite key), and the service checks the household.
- The schema below is the target for all phases. Phase 2 creates sections 5.1, 5.2, 5.5 (`events` only) and 5.6 in its first migration; later phases add their tables in new migration files. Never edit a migration that has been merged.

### 5.1 Identity

```sql
CREATE TABLE currencies (
    code            TEXT PRIMARY KEY CHECK (length(code) = 3 AND code = upper(code)),
    name            TEXT NOT NULL,
    symbol          TEXT NOT NULL,
    decimal_places  INTEGER NOT NULL CHECK (decimal_places BETWEEN 0 AND 8)
) STRICT;

CREATE TABLE households (
    id                TEXT PRIMARY KEY,
    name              TEXT NOT NULL,
    primary_currency  TEXT NOT NULL REFERENCES currencies (code),
    timezone          TEXT NOT NULL DEFAULT 'UTC',
    created_at        TEXT NOT NULL,
    updated_at        TEXT NOT NULL
) STRICT;

CREATE TABLE users (
    id             TEXT PRIMARY KEY,
    email          TEXT NOT NULL UNIQUE COLLATE NOCASE,
    display_name   TEXT NOT NULL,
    password_hash  TEXT NOT NULL,
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL
) STRICT;

CREATE TABLE household_members (
    household_id  TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    user_id       TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    role          TEXT NOT NULL CHECK (role IN ('owner', 'member')),
    created_at    TEXT NOT NULL,
    PRIMARY KEY (household_id, user_id)
) STRICT;

-- Browser/desktop sessions and personal access tokens share one table.
-- Only the SHA-256 of the token is stored.
CREATE TABLE sessions (
    id            TEXT PRIMARY KEY,
    user_id       TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    household_id  TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    kind          TEXT NOT NULL CHECK (kind IN ('session', 'token')),
    name          TEXT,
    token_hash    TEXT NOT NULL UNIQUE,
    created_at    TEXT NOT NULL,
    last_used_at  TEXT,
    expires_at    TEXT
) STRICT;
CREATE INDEX sessions_user ON sessions (user_id);
```

### 5.2 Ledger

```sql
CREATE TABLE accounts (
    id                    TEXT PRIMARY KEY,
    household_id          TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    owner_user_id         TEXT REFERENCES users (id) ON DELETE SET NULL,   -- NULL = joint
    name                  TEXT NOT NULL,
    type                  TEXT NOT NULL CHECK (type IN ('asset', 'expense', 'revenue', 'liability', 'equity')),
    equity_role           TEXT CHECK (equity_role IN ('opening_balance', 'reconciliation')),
    asset_role            TEXT CHECK (asset_role IN ('default', 'shared', 'savings', 'credit_card', 'cash_wallet')),
    liability_type        TEXT CHECK (liability_type IN ('loan', 'debt', 'mortgage')),
    liability_direction   TEXT CHECK (liability_direction IN ('i_owe', 'owed_to_me')),
    interest_rate         TEXT,                                            -- decimal string, percent
    interest_period       TEXT CHECK (interest_period IN ('daily', 'weekly', 'monthly', 'quarterly', 'half_year', 'yearly')),
    currency_code         TEXT NOT NULL REFERENCES currencies (code),
    iban                  TEXT,
    bic                   TEXT,
    account_number        TEXT,
    virtual_balance_minor INTEGER NOT NULL DEFAULT 0,
    include_net_worth     INTEGER NOT NULL DEFAULT 1 CHECK (include_net_worth IN (0, 1)),
    active                INTEGER NOT NULL DEFAULT 1 CHECK (active IN (0, 1)),
    sort_order            INTEGER NOT NULL DEFAULT 0,
    notes                 TEXT,
    created_at            TEXT NOT NULL,
    updated_at            TEXT NOT NULL,
    UNIQUE (household_id, id),
    UNIQUE (household_id, type, name),
    CHECK ((type = 'equity') = (equity_role IS NOT NULL)),
    CHECK (asset_role IS NULL OR type = 'asset'),
    CHECK (liability_type IS NULL OR type = 'liability')
) STRICT;
CREATE UNIQUE INDEX accounts_one_equity_per_role
    ON accounts (household_id, equity_role) WHERE equity_role IS NOT NULL;

CREATE TABLE categories (
    id            TEXT PRIMARY KEY,
    household_id  TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    name          TEXT NOT NULL,
    notes         TEXT,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    UNIQUE (household_id, name)
) STRICT;

CREATE TABLE tags (
    id            TEXT PRIMARY KEY,
    household_id  TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    name          TEXT NOT NULL,
    description   TEXT,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    UNIQUE (household_id, name)
) STRICT;

CREATE TABLE transaction_groups (
    id                  TEXT PRIMARY KEY,
    household_id        TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    title               TEXT,
    created_by_user_id  TEXT REFERENCES users (id) ON DELETE SET NULL,
    recurrence_id       TEXT,          -- set when generated by a recurrence (FK added in Phase 5)
    recurrence_date     TEXT,
    created_at          TEXT NOT NULL,
    updated_at          TEXT NOT NULL,
    UNIQUE (household_id, id),
    UNIQUE (recurrence_id, recurrence_date)   -- a recurrence fires at most once per date
) STRICT;

CREATE TABLE splits (
    id                      TEXT PRIMARY KEY,
    household_id            TEXT NOT NULL,
    group_id                TEXT NOT NULL,
    position                INTEGER NOT NULL,
    kind                    TEXT NOT NULL CHECK (kind IN ('withdrawal', 'deposit', 'transfer', 'opening_balance', 'reconciliation')),
    date                    TEXT NOT NULL,
    description             TEXT NOT NULL,
    source_account_id       TEXT NOT NULL,
    destination_account_id  TEXT NOT NULL,
    amount_minor            INTEGER NOT NULL CHECK (amount_minor > 0),
    currency_code           TEXT NOT NULL REFERENCES currencies (code),
    foreign_amount_minor    INTEGER CHECK (foreign_amount_minor > 0),
    foreign_currency_code   TEXT REFERENCES currencies (code),
    category_id             TEXT REFERENCES categories (id) ON DELETE SET NULL,
    budget_id               TEXT,      -- FK to budgets added in Phase 5
    bill_id                 TEXT,      -- FK to bills added in Phase 5
    reconciled              INTEGER NOT NULL DEFAULT 0 CHECK (reconciled IN (0, 1)),
    notes                   TEXT,
    meta                    TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(meta)),
    created_at              TEXT NOT NULL,
    updated_at              TEXT NOT NULL,
    UNIQUE (household_id, id),
    UNIQUE (group_id, position),
    FOREIGN KEY (household_id, group_id) REFERENCES transaction_groups (household_id, id) ON DELETE CASCADE,
    FOREIGN KEY (household_id, source_account_id) REFERENCES accounts (household_id, id),
    FOREIGN KEY (household_id, destination_account_id) REFERENCES accounts (household_id, id),
    CHECK (source_account_id <> destination_account_id),
    CHECK ((foreign_amount_minor IS NULL) = (foreign_currency_code IS NULL)),
    CHECK (foreign_currency_code IS NULL OR foreign_currency_code <> currency_code)
) STRICT;
CREATE INDEX splits_household_date ON splits (household_id, date);
CREATE INDEX splits_source_date ON splits (source_account_id, date);
CREATE INDEX splits_destination_date ON splits (destination_account_id, date);
CREATE INDEX splits_category ON splits (category_id);
CREATE INDEX splits_budget ON splits (budget_id);
CREATE INDEX splits_bill ON splits (bill_id);

CREATE TABLE split_tags (
    split_id  TEXT NOT NULL REFERENCES splits (id) ON DELETE CASCADE,
    tag_id    TEXT NOT NULL REFERENCES tags (id) ON DELETE CASCADE,
    PRIMARY KEY (split_id, tag_id)
) STRICT;
CREATE INDEX split_tags_tag ON split_tags (tag_id);

-- File content lives on disk at <data dir>/attachments/<sha256>.
CREATE TABLE attachments (
    id               TEXT PRIMARY KEY,
    household_id     TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    attachable_type  TEXT NOT NULL CHECK (attachable_type IN ('split', 'account', 'bill', 'budget', 'piggy_bank', 'tag')),
    attachable_id    TEXT NOT NULL,
    filename         TEXT NOT NULL,
    title            TEXT,
    mime_type        TEXT NOT NULL,
    size_bytes       INTEGER NOT NULL,
    sha256           TEXT NOT NULL,
    notes            TEXT,
    created_at       TEXT NOT NULL
) STRICT;
CREATE INDEX attachments_target ON attachments (attachable_type, attachable_id);
```

SQLite cannot add a foreign key to an existing column. In Phase 5, `splits.budget_id`, `splits.bill_id` and `transaction_groups.recurrence_id` stay plain columns; the services check that the referenced row exists in the same household, and deleting a budget, bill or recurrence clears the references in the same transaction.

### 5.3 Planning: budgets, bills, piggy banks

```sql

-- One row per due date. The scheduler creates them; reminders are tracked here.

    currency_code        TEXT NOT NULL REFERENCES currencies (code),
    start_date           TEXT,

CREATE TABLE piggy_bank_accounts (
    household_id   TEXT NOT NULL,
    piggy_bank_id  TEXT NOT NULL,

    PRIMARY KEY (piggy_bank_id, account_id),
    FOREIGN KEY (household_id, piggy_bank_id) REFERENCES piggy_banks (household_id, id) ON DELETE CASCADE,

    account_id     TEXT NOT NULL,

    split_id       TEXT REFERENCES splits (id) ON DELETE SET NULL,

    created_at     TEXT NOT NULL,

) STRICT;
CREATE INDEX piggy_bank_events_piggy ON piggy_bank_events (piggy_bank_id, date);
```

When the split that paid a bill period is deleted, the service sets the period back to `open` in the same transaction.

### 5.4 Planning: recurring transactions and rules

```sql
CREATE TABLE recurrences (
    id               TEXT PRIMARY KEY,
```

## 6. API

Base path `/api/v1`. JSON only. The OpenAPI document is served at `/api/v1/openapi.json` and written to `web/openapi.json` by `saldo openapi`, so the TypeScript client can be generated without a running server.

Conventions:

- Success: `{ "data": ..., "meta": { "page": 1, "per_page": 50, "total": 1234 } }` (`meta` only on lists). Error: `{ "error": { "code": "validation_failed", "message": "...", "details": [ { "field": "splits[1].amount", "code": "amount_not_positive", "message": "..." } ] } }`.
- Status codes: 200, 201, 204, 400 (malformed), 401, 403, 404, 409 (conflict, e.g. duplicate name), 422 (validation), 429, 500.
- Amounts in JSON are decimal strings plus a currency code: `{ "amount": "12.50", "currency": "EUR" }`. Never JSON numbers.
- Lists take `page`, `per_page` (max 200) and resource filters. Sorting is fixed per resource.
- Every list and report takes `scope=household` (default), `scope=mine`, or `scope=user:<id>`, filtering by account owner.
- A transaction group is always written as a whole: `POST` creates the group with its splits, `PUT` replaces it, `DELETE` removes it. There are no per-split write endpoints.

## 7. Auth and household

- Passwords are hashed with Argon2id. Login is rate-limited per IP and per email.
- A login creates a `sessions` row and returns a random 256-bit token. The web app receives it as a cookie `saldo_session` (HttpOnly, SameSite=Lax, and Secure when `SALDO_PUBLIC_URL` is https). The token is never in the login response body. Desktop, scripts and the importer send `Authorization: Bearer <token>`. Personal access tokens are rows of kind `token`, shown once at creation.
- CSRF: a request authenticated by cookie that is not GET/HEAD must carry the header `X-Saldo-Csrf: 1` and an `Origin` matching `SALDO_PUBLIC_URL`. Bearer requests are exempt.
- First run: `POST /setup` creates the first user and the household, and only works while the `users` table is empty. The same is available as `saldo user create`.
- An owner adds members with an initial password. v1 has no email invitations and no password-reset email.
- Authorization in v1 is household membership: a member can read and write everything in the household. Owner-only: managing members, webhooks, export and household settings.
- Every request resolves to a `HouseholdCtx { household_id, user_id, role }`. Every service and repository function takes it as its first parameter and puts `household_id` in every query. There is no way to call a repository without one. (Laravel analogy: a global scope that cannot be removed. Go analogy: a `context.Context` value that is a required typed argument instead of a hidden key.)

## 8. Events, webhooks, notifications

### 8.1 Event log

Every state change is one service method that opens a transaction, validates through `core`, writes the rows, appends one `events` row, and commits. If the event insert fails, the change is rolled back.

Event types are `<entity>.<verb>`:

- CRUD: `account.*`, `transaction.*`, `category.*`, `tag.*`, `budget.*`, `budget_limit.*`, `bill.*`, `piggy_bank.*`, `recurrence.*`, `rule.*`, `household_member.*`, `webhook.*`, each with `created`, `updated`, `deleted`; also `household.created` (setup) and `household.updated`.
- Setup appends four events in its one transaction: `household.created`, `household_member.created` and two `account.created` (the equity accounts).
- Sessions and API tokens (login, logout, token create/revoke) are authentication state, not household data, and append no event.
- The entity in `data` is the `saldo-app` view type (`AccountView`, `TransactionGroupView`, ...), which is also the API response, so the two cannot drift.
- Domain: `bill.due_soon`, `bill.overdue`, `bill.paid`, `bill.period_reopened`, `recurrence.fired`, `piggy_bank.target_reached`, `import.completed`, `webhook.test`.

Payload, also the webhook body:

```json
{
  "id": "0193c1a2-...",
  "type": "transaction.created",
  "occurred_at": "2026-11-11T20:21:00.000Z",
  "household_id": "0193...",
  "actor": { "user_id": "0193..." },
  "origin": "api",
  "data": { "...": "the full entity as the API returns it; for deleted, the last state" }
}
```

A `transaction.*` event carries the whole group with all its splits.

### 8.2 Webhook delivery

- A dispatcher task reads events after the `webhooks` cursor, inserts a `webhook_deliveries` row for every active endpoint whose `event_types` match (events with origin `import` only if `include_import_events`), then advances the cursor, all in one transaction.
- A delivery worker picks `pending` rows whose `next_attempt_at` has passed and POSTs the payload with a 10 second timeout and no redirects.
- Headers: `Content-Type: application/json`, `User-Agent: Saldo-Webhook/<version>`, `X-Saldo-Event-Id`, `X-Saldo-Event-Type`, `X-Saldo-Delivery-Id`, `X-Saldo-Signature: t=<unix seconds>,v1=<hex>` where `v1 = HMAC-SHA256(secret, "<t>." + raw body)`. Receivers should reject timestamps older than 5 minutes and compare in constant time.
- Any 2xx is success. Otherwise retry with exponential backoff and jitter: 1 min, 5 min, 30 min, 2 h, 6 h, 12 h, 24 h; after 8 attempts the delivery is `dead`. An endpoint with 20 consecutive dead deliveries is deactivated with a `disabled_reason`.
- Deliveries are at-least-once and may arrive out of order; receivers deduplicate on `X-Saldo-Event-Id`.
- Private addresses are allowed as targets (Home Assistant, n8n on the LAN are the main use). Only owners manage endpoints; URLs must be `http` or `https`.

### 8.3 Bill reminders

A scheduler task runs at startup and every 15 minutes. For every active bill, using the household's timezone for "today":

1. Create missing `bill_periods` rows from `first_due_date` up to 60 days ahead.
2. For each `open` period, call `core::reminder_due`. If today ≥ `due_date − remind_days_before` and no reminder was sent yet, emit `bill.due_soon`. If today > `due_date` and at least `remind_every_days` have passed since `last_reminded_on`, emit `bill.overdue`. Update `last_reminded_on` and `reminder_count` in the same transaction as the event.

A period becomes `paid` when a split is linked to it: explicitly through `POST /bill-periods/{id}/pay`, or automatically when a split with `bill_id` set is saved with a date in the period's window (from the previous due date to the next). Rules can set `bill_id` with the `link_to_bill` action. Paying emits `bill.paid` and stops reminders.

### 8.4 Notifications

A notifier task reads events after the `notifications` cursor. For `bill.due_soon` and `bill.overdue` (more types later) it inserts one `notifications` row per active channel of every household member, with a dedupe key, then sends:

- `ntfy` / `gotify`: an HTTP POST to the configured server and topic/token.
- `email`: SMTP, configured by `SALDO_SMTP_*`.
- `webpush`: Web Push with VAPID keys; the channel `config` holds the browser's push subscription.

Failed sends are retried three times, then marked `failed`.

### 8.5 Background tasks

All tasks (dispatcher, delivery worker, scheduler, notifier, recurrence runner) are Tokio tasks started by `saldo serve`, stopped on SIGTERM through a shared cancellation token. Time comes from a `Clock` trait so tests can use a fake clock. Each task must be safe to run again after a crash at any point: all progress is in the database.

## 9. Importer and export

### 9.1 Firefly III importer

`saldo-import firefly --url <firefly url> --token-env <VAR, default FIREFLY_TOKEN> --household <id or name> [--dry-run] [--only accounts,transactions,...] [--since YYYY-MM-DD] [--allow-mismatch]`. The token is read from an environment variable, never an argument. It opens the Saldo database directly (`SALDO_DATABASE_URL`, files under `SALDO_DATA_DIR`) and calls the `saldo-app` services' `<method>_in` variants with origin `import`, all in one database transaction per run (rolled back on `--dry-run`). It only ever sends GET requests to Firefly. It can run while the server is running (WAL mode).

Facts from the Firefly III OpenAPI spec v6.7.8:

- Auth: `Authorization: Bearer <token>`. Lists take `limit` and `page`; the response has `meta.pagination.total_pages`. Default page size is 50.
- Amounts are decimal strings; every object carries `currency_code` and `currency_decimal_places`. Fields prefixed `pc_` are primary-currency conversions and are ignored.
- A transaction is a group (`group_title`, `transactions[]`); each split has `transaction_journal_id`, `type`, `date`, `amount`, `foreign_amount`, `source_id`, `source_type`, `destination_id`, `destination_type`, `category_id`, `budget_id`, `subscription_id` (`bill_id` is the deprecated name), `tags[]` (names), `reconciled`, `notes`, and more.
- Bills are now called subscriptions: use `/v1/subscriptions`.

Import order and mapping:

| # | Firefly endpoint | Saldo | Notes |
|---|---|---|---|
| 1 | `/v1/currencies` | `currencies` | Only enabled ones; fail if `decimal_places` > 8 |
| 2 | `/v1/accounts` | `accounts` | `asset`, `expense`, `revenue`, `liability`/`liabilities` map directly. `initial-balance` → the Equity(OpeningBalance) account; `reconciliation` → Equity(Reconciliation); `cash` → an expense account and a revenue account both named `(cash)`, picked by direction; `import` accounts are skipped and reported. `account_role` `defaultAsset/sharedAsset/savingAsset/ccAsset/cashWalletAsset` → `asset_role`. Opening balances arrive as transactions, not from the account fields |
| 3 | `/v1/categories`, `/v1/tags` | `categories`, `tags` | |
| 4 | `/v1/budgets`, `/v1/budgets/{id}/limits` | `budgets`, `budget_limits` | auto-budget fields map 1:1 (`none` → NULL) |
| 5 | `/v1/subscriptions` | `bills`, `bill_periods` | `date` → `first_due_date`; `paid_dates[]` → paid periods linked to the imported split |
| 6 | `/v1/piggy-banks`, `/v1/piggy-banks/{id}/events` | `piggy_banks`, `piggy_bank_accounts`, `piggy_bank_events` | |
| 7 | `/v1/rule-groups`, `/v1/rules` | `rule_groups`, `rules`, triggers, actions | Unsupported keywords: the rule is imported inactive and listed in the report |
| 8 | `/v1/recurrences` | `recurrences`, repetitions, splits | `ndom` → `nth_weekday`; weekend 1-4 → `keep/skip/previous_friday/next_monday` |
| 9 | `/v1/transactions` | `transaction_groups`, `splits`, `split_tags` | Paged by date range. Kind is derived by Saldo and compared with Firefly's `type`; a mismatch is reported. SEPA fields, the extra dates, `internal_reference`, `external_url`, `external_id`, `original_source`, `import_hash_v2` and the original date-time go into `meta.firefly` |
| 10 | `/v1/attachments` + download | `attachments` + files | |

Idempotency: for every object, look up `external_refs (household, 'firefly-iii', entity_type, firefly id)`. If found, update the local row; if not, create it and insert the ref, in one transaction. A split's external ID is its `transaction_journal_id`; a group's is the group ID. Splits that disappeared from a Firefly group are deleted locally on re-import.

Verification, printed at the end of every run and stored in `import_runs.summary`: counts per entity (created / updated / unchanged / skipped), every skipped or downgraded item with the reason, and a balance check comparing each asset and liability account's computed balance with Firefly's `current_balance`.

Checked against the owner's Firefly 6.7.9 in Phase 3; the answers are in `docs/STATUS.md` under "Findings about Firefly III" (notably: transactions are paged by split, list them with `type=all`, amounts carry 12 decimals). Originally unconfirmed: how liability `liability_direction` (`credit`/`debit`) affects signs; the exact shape of piggy bank `accounts[]`; whether `/v1/transaction-links` exposes the link type on read; the maximum `limit`; whether Firefly really forces one shared source or destination per split group (Saldo does not care, but the kind comparison might).

### 9.2 Export

- `GET /api/v1/export/json` and `saldo export json`: one document `{ "format": "saldo-export", "version": 1, "exported_at": ..., "household": ..., "currencies": [...], "accounts": [...], "transactions": [...], ... }` with every table of the household, using the API's own representations. It is complete enough to rebuild the household.
- `GET /api/v1/export/csv` and `saldo export csv`: a zip with one CSV per entity. `transactions.csv` is one row per split with account names, category, tags and decimal amounts, so it opens directly in a spreadsheet.
- The SQLite file itself is the third way out: `saldo backup <path>` runs `VACUUM INTO`.

## 10. Frontend

| Option | For | Against |
|---|---|---|
| **React + TypeScript SPA (Vite), PWA, Tauri 2 desktop** | One codebase for web, desktop and mobile; typed client generated from OpenAPI; the largest ecosystem (TanStack Query and Router, shadcn/ui, charts); Tauri uses the system webview, roughly a tenth of Electron's memory; the built SPA is embedded in the server binary, so there is still one Docker image | A second language and toolchain; iOS delivers Web Push only to an installed PWA |
| The same with Vue or Svelte | Vue is familiar from Laravel; Svelte has the smallest bundles | Smaller component and chart ecosystems; no decisive gain |
| All-Rust UI (Dioxus, Leptos) | Shares types with `saldo-core`; one language | Doubles the Rust learning load on the hardest part (UI state and lifetimes); few ready-made components; larger WASM payload; mobile is immature |
| t3code style (TS monorepo, Electron, WebSocket RPC) | Proven for realtime-heavy apps | Electron's memory use; an RPC layer is unnecessary for CRUD and reports |
| Flutter, React Native | True native mobile | A third stack; a PWA is enough here |

Chosen: React + TypeScript + Vite, TanStack Query (server state) and TanStack Router, shadcn/ui components on Tailwind, Recharts for charts, `openapi-typescript` + `openapi-fetch` for the generated client, `vite-plugin-pwa` for the service worker.

- `web/src/api/` holds the generated client and is the only code that knows URLs. Its base URL is configurable, because the Tauri app talks to a remote server while the web app uses the same origin.
- The server serves the built SPA from the binary (`rust-embed`) for every path outside `/api`.
- Live updates: the SPA listens to `/api/v1/events/stream` and invalidates the matching queries, so a change made by one household member appears for the other.
- Desktop (Phase 7): a Tauri 2 shell loading the same build, with a first-run screen asking for the server URL, bearer-token auth stored in the OS keychain, and native notifications.

## 11. Deployment

- One image built in stages: Node builds `web/`, Rust builds the two binaries (with `cargo-chef` for layer caching), the final stage is a slim Debian image running as a non-root user.
- One volume `/data`: `saldo.db` (plus WAL files) and `attachments/`.
- `docker-compose.yml` with the single service, the volume, a health check on `/healthz`, and an `.env.example`.
- Configuration by environment variables: `SALDO_DATABASE_URL` (default `sqlite:///data/saldo.db`), `SALDO_DATA_DIR`, `SALDO_BIND` (default `0.0.0.0:8080`), `SALDO_PUBLIC_URL`, `SALDO_SMTP_HOST/PORT/USER/PASSWORD/FROM`, `SALDO_VAPID_PRIVATE_KEY`, `SALDO_LOG` (level). The server refuses to start with invalid configuration and says which variable is wrong.
- Migrations run at startup. TLS is expected from a reverse proxy.
- Logs are structured (`tracing`), one line per request with a request ID; secrets and tokens are never logged.

## 12. Testing

- Tests are written first. Target: 80% line coverage measured by `cargo llvm-cov`, with `saldo-core` close to 100%.
- `saldo-core`: unit tests next to the code, and `proptest` properties for money arithmetic, kind derivation, ledger balance (sum of all balances is zero) and schedules.
- `saldo-app`: integration tests against an in-memory SQLite database with the real migrations (`#[sqlx::test]`). Every service test also asserts the event row.
- `saldo-server`: API tests that call the Axum router in-process (`tower::ServiceExt::oneshot`), no network. One test asserts that the generated OpenAPI document matches the committed `web/openapi.json`.
- `saldo-importer`: recorded Firefly JSON fixtures served by `wiremock`; one test runs the import twice and asserts that the second run changes nothing.
- Web: Vitest for logic, Playwright for the main flows (login, create a split transaction, see balances).
- CI on every push: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, and from Phase 4 the web lint, type check and tests.
