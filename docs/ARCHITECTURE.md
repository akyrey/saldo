# Saldo architecture

Saldo is a self-hosted personal finance server for one household, built to replace Firefly III. This document is the contract every phase works against. Changing it needs the owner's approval; record the change in `docs/STATUS.md`.

Contents: [1 Goals](#1-goals) · [2 Decisions](#2-decisions) · [3 Crates](#3-crates) · [4 Domain model](#4-domain-model) · [5 SQL schema](#5-sql-schema) · [6 API](#6-api) · [7 Auth and household](#7-auth-and-household) · [8 Events, webhooks, notifications](#8-events-webhooks-notifications) · [9 Importer and export](#9-importer-and-export) · [10 Frontend](#10-frontend) · [11 Deployment](#11-deployment) · [12 Testing](#12-testing)

## 1. Goals

- Firefly III core features: asset, expense, revenue and liability accounts, transactions, categories, tags, budgets, bills, piggy banks, recurring transactions, rules, reports.
- Four things Firefly III lacks:
  1. Split transactions where every split has its own source and destination account.
  2. Bill reminders: one a few days before the due date, then repeated until the bill is paid.
  3. Webhooks for every domain event, with retries and HMAC signatures.
  4. A household: several users, each with their own accounts, and a combined view.
- No lock-in: an idempotent importer from Firefly III, and JSON/CSV export from the first usable version.
- One server, three clients (web, desktop, mobile). Always online; no offline sync.

## 2. Decisions

| Topic | Decision | Why |
|---|---|---|
| Name | Saldo: crates `saldo-*`, binaries `saldo` and `saldo-import`, headers `X-Saldo-*`, env vars `SALDO_*` | |
| Language, runtime | Rust, Tokio, Axum | |
| Database | SQLite only, through SQLx with compile-time checked queries | One file to back up, one container; household scale |
| Money | `i64` minor units + ISO currency code, never floats | Exact arithmetic |
| IDs | UUIDv7 stored as TEXT | Sortable by creation time like ULID, but an IETF standard (RFC 9562) supported directly by `uuid`, SQLx, utoipa and OpenAPI `format: uuid` |
| Dates | A split has a calendar `date` (`YYYY-MM-DD`). Audit timestamps are UTC RFC 3339 (`2026-11-11T20:21:00.000Z`) | Finance is date-based; no timezone maths in SQL |
| Currencies | One primary currency per household, optional foreign amount per split, no exchange-rate table in v1 | Owner uses one currency with rare foreign purchases |
| Household visibility | Every member sees and edits everything; accounts have an owner for mine / member / household filters | Owner's choice |
| Auth | Password (Argon2id) + server-side sessions + personal access tokens; OIDC later | |
| API | REST under `/api/v1`, OpenAPI generated by utoipa | Typed clients for any frontend |
| Event log | Appended in the same DB transaction as every change, starting in Phase 2 | Outbox pattern; it is an audit log, not event sourcing |
| Import identity | `external_refs` mapping table | Firefly splits have their own user-facing `external_id`, which is kept separately |
| Frontend | React + TypeScript SPA (Vite), PWA for mobile, Tauri 2 for desktop | See section 10 |
| Notifications | ntfy/Gotify, SMTP email, Web Push, and webhooks | |
| Deployment | One Docker image + docker-compose, data in one volume | |

## 3. Crates

```
Cargo.toml                 workspace, shared dependency versions and lints
crates/core/               saldo-core      pure domain: no I/O, no async, no SQL
crates/app/                saldo-app       services (use cases), SQLx repositories, migrations/, response views
crates/server/             saldo-server    binary `saldo`: Axum API, auth, OpenAPI, background workers, embedded SPA
crates/importer/           saldo-importer  binary `saldo-import`: Firefly III API client and mapping
web/                       React SPA (Phase 4), TS client generated from openapi.json
desktop/                   Tauri 2 shell around web/ (Phase 7)
docs/                      this file, PLAN.md, STATUS.md, phases/
```

Dependency direction: `core` ← `app` ← `server`, and `core` ← `app` ← `importer`. Nothing depends on `server`.

Laravel analogy: `core` is plain value objects and domain rules with no framework; `app` is Eloquent models, service classes and migrations; `server` is routes, controllers, middleware and queue workers; `importer` is an artisan command. Go analogy: `core` is a package importing only the standard library; `app` is the package holding `*sql.DB` code; `server` and `importer` are two `cmd/` binaries.

Why `saldo-app` exists: the server and the importer both go through the same services, so imported data passes the same validation and writes the same events as API calls, without the importer speaking HTTP or duplicating SQL.

Rules for all crates:

- `saldo-core` has no dependency that does I/O. Allowed: `uuid`, `chrono` (no `clock` feature), `serde`, `serde_json` (only for the free-form `SplitMeta` object), `thiserror`.
- The current time and new IDs come from outside `core` (parameters or the `Clock` trait in `app`), so tests are deterministic.
- Add dependencies with `cargo add`, so versions are current; shared ones go in `[workspace.dependencies]`.
- `unsafe` is forbidden (`#![forbid(unsafe_code)]`); `unwrap()` and `expect()` only in tests.

## 4. Domain model

This is the shape of the Rust types in `saldo-core`. Names and invariants are binding; field order and derive lists are not.

```rust
// Newtype IDs: a struct wrapping one value, so an AccountId can never be passed
// where a SplitId is expected. (PHP/Go: like `type AccountID string` in Go, but
// the compiler refuses implicit conversion.)
pub struct AccountId(pub Uuid);       // same pattern: HouseholdId, UserId, GroupId,
                                      // SplitId, CategoryId, TagId, BudgetId, BillId, ...

pub struct CurrencyCode(/* 3 uppercase ASCII letters */);
pub struct Currency { code: CurrencyCode, decimal_places: u8 }   // private; Currency::new checks 0..=8

pub struct Money { minor: i64, currency: CurrencyCode }
// Money::parse_decimal("123.45", &eur) -> Ok(12345); "1.234" with 2 places -> Err
// checked_add / checked_sub return Err on overflow or currency mismatch
// to_decimal_string(&eur) -> "123.45"

pub enum AccountType {
    Asset,
    Expense,
    Revenue,
    Liability,
    Equity(EquityRole),               // system accounts, one of each per household
}
pub enum EquityRole { OpeningBalance, Reconciliation }

pub struct Account {
    pub id: AccountId,
    pub household_id: HouseholdId,
    pub owner: Option<UserId>,        // None = joint
    pub name: String,
    pub account_type: AccountType,    // immutable after creation
    pub currency: CurrencyCode,
    pub active: bool,
    // asset role, liability details, iban, ... see the accounts table
}

pub enum SplitKind { Withdrawal, Deposit, Transfer, OpeningBalance, Reconciliation }

pub struct NewSplit {                 // input, not yet validated
    pub date: NaiveDate,
    pub description: String,
    pub source: AccountId,
    pub destination: AccountId,
    pub amount: Money,                // always > 0, flows source -> destination
    pub foreign_amount: Option<Money>,
    pub category: Option<CategoryId>,
    pub budget: Option<BudgetId>,
    pub bill: Option<BillId>,
    pub tags: Vec<TagId>,
    pub reconciled: bool,
    pub notes: Option<String>,
    pub meta: SplitMeta,              // free-form extra fields (SEPA, extra dates, references)
}
pub struct NewTransactionGroup { pub title: Option<String>, pub splits: Vec<NewSplit> }

// Validation turns input into a type that can only exist if it is valid
// ("parse, don't validate"). Services accept only ValidatedGroup.
pub fn validate_group(
    input: NewTransactionGroup,
    accounts: &AccountLookup,         // the accounts referenced, loaded by the caller
) -> Result<ValidatedGroup, Vec<ValidationError>>;

// What validation needs from the database, loaded by the caller: the household,
// the referenced accounts, and the category/budget/bill/tag IDs that exist in that
// household. Anything missing from the lookup counts as unknown.
pub struct AccountLookup { /* private */ }
// AccountLookup::new(household_id).with_account(a).with_category(id).with_tag(id)...

// Balances: two deltas per split (source -amount, destination +amount, or the
// foreign amount for an account in the foreign currency), folded into a map.
pub fn balance_deltas(group: &ValidatedGroup, accounts: &AccountLookup) -> Vec<(AccountId, Money)>;
pub fn apply_deltas(balances: BTreeMap<AccountId, Money>, deltas: &[(AccountId, Money)])
    -> Result<BTreeMap<AccountId, Money>, MoneyError>;
```

`ValidationError` has one variant per broken rule; each split-level variant carries the zero-based `split` index, and `code()` returns a stable string: `empty_group`, `amount_not_positive`, `same_account`, `unknown_account`, `account_outside_household`, `unknown_reference` (category, budget, bill or tag), `invalid_account_pair`, `account_inactive`, `currency_mismatch`, `foreign_amount_not_positive`, `foreign_currency_same_as_amount`, `foreign_amount_required`, `foreign_currency_mismatch`. Its JSON form is `{"code": "...", "split": 0, ...}`.

### 4.1 Split kind

Derived from the two account types and stored on the split. Account type never changes, so the stored value never goes stale.

| Source | Destination | Kind |
|---|---|---|
| Asset, Liability | Expense | Withdrawal |
| Revenue | Asset, Liability | Deposit |
| Asset, Liability | Asset, Liability | Transfer |
| Equity(OpeningBalance) | Asset, Liability (or the reverse) | OpeningBalance |
| Equity(Reconciliation) | Asset, Liability (or the reverse) | Reconciliation |
| anything else | | `ValidationError::InvalidAccountPair` |

A refund is a Deposit from a Revenue account, as in Firefly III.

`SplitKind::derive(source: AccountType, destination: AccountType) -> Result<SplitKind, InvalidAccountPair>`, where `InvalidAccountPair { source, destination }` holds the two types; `validate_group` turns it into `ValidationError::InvalidAccountPair` with the split index.

### 4.2 Ledger invariants

All enforced in `saldo-core`, unit-tested and property-tested; the ones marked (DB) are also SQL constraints.

1. A group has at least one split.
2. `amount > 0` (DB).
3. `source != destination` (DB).
4. The account pair gives a valid kind (4.1).
5. All accounts, categories, budgets, bills and tags belong to the group's household (DB for accounts).
6. Split currency: for Withdrawal and Deposit, the currency of the Asset/Liability side; for Transfer, the currency of the source; for OpeningBalance and Reconciliation, the currency of the Asset/Liability side.
7. `foreign_amount` is `> 0` and in a different currency than `amount` (DB). A Transfer between accounts with different currencies must have a foreign amount in the destination's currency.
8. Both accounts are active when a split is created (editing old splits on archived accounts is allowed).
9. Splits in one group may have different sources, destinations, kinds and dates.

Balance of an account = sum of amounts where it is the destination − sum where it is the source (using the foreign amount when the account's currency is the split's foreign currency). Every split moves money from one account to another, so the ledger is double-entry by construction and the sum of all balances is always zero per currency. Sign convention: Asset positive = you have money; Liability negative = you owe; Expense positive = spent; Revenue negative = earned.

### 4.3 Other domain logic in `core`

- **Schedules**: bills and recurrences each have their own schedule type (built in parallel in Phase 5): `bills::BillSchedule` (weekly, monthly, quarterly, half-year, yearly, with `skip`; `occurrences(from, to)`, `matching_due_date`) and `recurrence::RecurrenceSchedule` with `recurrence::occurrences(schedule, from, to) -> Vec<NaiveDate>` (daily, weekly, monthly, nth weekday, yearly, with `skip`, a weekend policy, `repeat_until` and `max_occurrences`). Month-end is clamped (31st → 30th/28th). Pure functions; today's date is a parameter.
- **Rules**: `Trigger` and `Action` are enums whose variants carry data, for example `Trigger::DescriptionContains(String)`, `Trigger::AmountMoreThan(i64)`, `Action::SetCategory(CategoryId)`, `Action::LinkToBill(BillId)`. `fn evaluate(rule: &Rule, split: &SplitView) -> Vec<Action>` is pure; applying the actions is a service in `app`.
- **Bill history** (Phase 11): `bill_history::history_span(SpanInput) -> HistorySpan` (the dates `GET /bills/{id}/history` covers, see section 6), `due_status(stored, due, today) -> DueStatus` (adds the derived `Overdue` and `Scheduled`), `payment_stats(amounts) -> Result<Option<PaymentStats>, MoneyError>` (count, total, average rounded half away from zero, min, max).
- **Bill reminders**: `fn reminder_due(period: &BillPeriod, bill: &Bill, today: NaiveDate) -> Option<ReminderKind>` decides `DueSoon` / `Overdue` / nothing.
- **Budget maths**: spent per budget limit, available amount, the limits an auto-budget creates (always its base amount), and the carry-over (Phase 9): `carry::carried(limits, spends, Carry) -> Vec<Money>` gives what each limit receives from the previous one in its currency. A limit carries only into one that starts the day after it ends; `leftover` passes on a positive rest, `all` a negative one too, `none` nothing. Computed when limits are read, never stored, so editing an older transaction updates every later limit.
- **Forecast** (Phase 9): `forecast::project(start, planned, intervals) -> Projection` adds planned amounts (dated, signed, one currency) to a starting balance and returns the balance at the end of each interval and the lowest end-of-day balance. Collecting the amounts is `app`'s job.
- **Subscription detection** (Phase 9): `subscriptions::detect_subscriptions(payments, today) -> Vec<Candidate>` groups withdrawals by counterparty and currency, drops a group with any payment already on a bill, keeps payments within 20% of the latest amount, and tries weekly (±2 days, 3 payments), monthly (±4, 3), quarterly (±7, 3), half-year (±10, 2) and yearly (±15, 2), shortest first. Each payment is compared with the date the schedule expected (a miss restarts the schedule from that payment); at least 75% of gaps must fit, and the next due date plus the tolerance must not be past.
- **Reconciliation** (Phase 9): `reconcile::reconcile(statement_balance, cleared) -> Option<Money>` is the statement balance minus the cleared signed amounts, `None` when they agree.
- **Credit card months** (Phase 12): `card_cycle::Cycle` is a calendar month (`YYYY-MM`, ordered, `settlement_date(day)` = that day of the following month, clamped to its last day). `effective_cycle(date, moved)` is the date's month, or the next one when moved; `cycle_spending(entries, cycle)` sums signed card entries (+ purchase, − refund) counting toward a month; `available(limit, spent)`; `limit_for(limits, cycle)` is the latest budget starting on or before the month. `settlement_step(SettlementInput) -> SettlementStep { change, next_state }` is the settlement decision table (5.4f): frozen and detached months are left alone; a stored transfer that differs from what the server wrote detaches the month; a reconciled one freezes it; otherwise the transfer is created, updated or deleted to equal the month's spending (none when zero or less), and from the settlement date on the month freezes after that last update. `is_closed(state, settlement_date, today)`: no more moves once frozen or from the settlement date.
- **Statement matching** (Phase 13, `matching`): text helpers (`normalise`, `tokens` = lowercase words of 3+ characters, `jaccard` and `coverage` in per-mille); `fingerprint(account, date, amount, text, occurrence)` (SHA-256 hex of the normalised line plus how many identical lines precede it) and `occurrences`; `assign(pairs, uses, pinned)`, the one ranked assignment every matcher uses: pinned pairs first, then pairs by `(score, more splits used first, line, candidate)`, taken greedily, skipping a pair whose line is taken or that uses a split already used, so a group and its own splits compete without a split being matched twice. `ledger_candidates(splits, account)` gives one candidate per split touching the account plus one per group whose splits share kind, currency, date and side (summed); amounts are signed for the account, so equal signed amounts also mean the same direction (a debit only matches a transfer out). `match_ledger(lines, candidates, window_days, range, pinned)` scores `days apart × 1000 − 3 × jaccard` (a line may carry its own asymmetric `LagWindow`, for transfers found through a transfer rule; a remembered pin wins whatever the amount and date, and a pin naming an unknown line or candidate is dropped) and classifies what is left in the statement range as a duplicate of a matched candidate, a duplicate of another leftover, or not on the statement. `classify_paypal`, `pair_paypal_funding` (a funding row and its payment share date and time; every funding takes its exact amount first, then the single payment left at its moment) and `match_paypal` (asymmetric lag window, `coverage` of the merchant name; leftovers only inside the statement range); `amazon_orders`, `find_order_ids` and `match_amazon` (order ID first whatever the amount, then exact amount in the window, then the closest amount within a tolerance, amount before date, marked approximate; a line naming any order ID, known or not, is never matched by amount; unmatched orders only inside the statement range); `split_by_item(charge, items)` (the difference goes to the largest item; `None` when a split would not stay positive); `statement_gap(opening, amounts, closing)` and `balances_at(closing, lines, dates)`.

## 5. SQL schema

SQLite with `STRICT` tables. Connection settings, applied by `saldo-app` on every connection: `foreign_keys = ON`, `journal_mode = WAL`, `busy_timeout = 5000`, `synchronous = NORMAL`.

Conventions:

- `id` is a UUIDv7 as lowercase hyphenated TEXT. Amounts are INTEGER minor units with a `currency_code`. Booleans are INTEGER 0/1. Dates are `YYYY-MM-DD`; timestamps are UTC RFC 3339 with milliseconds and `Z`, so text ordering is time ordering.
- Every domain table has `household_id`. Tables referenced by NOT NULL foreign keys have `UNIQUE (household_id, id)` so the reference can be a composite key, which makes cross-household references impossible at the database level. Nullable references use a single-column key with `ON DELETE SET NULL` (SQLite cannot null only one column of a composite key), and the service checks the household.
- The schema below is the target for all phases. Phase 2 creates sections 5.1, 5.2, 5.5 (`events` only) and 5.6 in its first migration; later phases add their tables in new migration files. Never edit a migration that has been merged.

### 5.1 Identity

```sql
CREATE TABLE currencies (
    code            TEXT PRIMARY KEY CHECK (length(code) = 3 AND code = upper(code)),
    name            TEXT NOT NULL,
    symbol          TEXT NOT NULL,
    decimal_places  INTEGER NOT NULL CHECK (decimal_places BETWEEN 0 AND 8)
) STRICT;

CREATE TABLE households (
    id                TEXT PRIMARY KEY,
    name              TEXT NOT NULL,
    primary_currency  TEXT NOT NULL REFERENCES currencies (code),
    timezone          TEXT NOT NULL DEFAULT 'UTC',
    created_at        TEXT NOT NULL,
    updated_at        TEXT NOT NULL
) STRICT;

CREATE TABLE users (
    id             TEXT PRIMARY KEY,
    email          TEXT NOT NULL UNIQUE COLLATE NOCASE,
    display_name   TEXT NOT NULL,
    password_hash  TEXT NOT NULL,
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL
) STRICT;

CREATE TABLE household_members (
    household_id  TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    user_id       TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    role          TEXT NOT NULL CHECK (role IN ('owner', 'member')),
    created_at    TEXT NOT NULL,
    PRIMARY KEY (household_id, user_id)
) STRICT;

-- Browser/desktop sessions and personal access tokens share one table.
-- Only the SHA-256 of the token is stored.
CREATE TABLE sessions (
    id            TEXT PRIMARY KEY,
    user_id       TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    household_id  TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    kind          TEXT NOT NULL CHECK (kind IN ('session', 'token')),
    name          TEXT,
    token_hash    TEXT NOT NULL UNIQUE,
    created_at    TEXT NOT NULL,
    last_used_at  TEXT,
    expires_at    TEXT
) STRICT;
CREATE INDEX sessions_user ON sessions (user_id);
```

### 5.2 Ledger

```sql
CREATE TABLE accounts (
    id                    TEXT PRIMARY KEY,
    household_id          TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    owner_user_id         TEXT REFERENCES users (id) ON DELETE SET NULL,   -- NULL = joint
    name                  TEXT NOT NULL,
    type                  TEXT NOT NULL CHECK (type IN ('asset', 'expense', 'revenue', 'liability', 'equity')),
    equity_role           TEXT CHECK (equity_role IN ('opening_balance', 'reconciliation')),
    asset_role            TEXT CHECK (asset_role IN ('default', 'shared', 'savings', 'credit_card', 'cash_wallet')),
    liability_type        TEXT CHECK (liability_type IN ('loan', 'debt', 'mortgage')),
    liability_direction   TEXT CHECK (liability_direction IN ('i_owe', 'owed_to_me')),
    interest_rate         TEXT,                                            -- decimal string, percent
    interest_period       TEXT CHECK (interest_period IN ('daily', 'weekly', 'monthly', 'quarterly', 'half_year', 'yearly')),
    currency_code         TEXT NOT NULL REFERENCES currencies (code),
    iban                  TEXT,
    bic                   TEXT,
    account_number        TEXT,
    virtual_balance_minor INTEGER NOT NULL DEFAULT 0,
    include_net_worth     INTEGER NOT NULL DEFAULT 1 CHECK (include_net_worth IN (0, 1)),
    active                INTEGER NOT NULL DEFAULT 1 CHECK (active IN (0, 1)),
    sort_order            INTEGER NOT NULL DEFAULT 0,
    notes                 TEXT,
    created_at            TEXT NOT NULL,
    updated_at            TEXT NOT NULL,
    UNIQUE (household_id, id),
    UNIQUE (household_id, type, name),
    CHECK ((type = 'equity') = (equity_role IS NOT NULL)),
    CHECK (asset_role IS NULL OR type = 'asset'),
    CHECK (liability_type IS NULL OR type = 'liability')
) STRICT;
CREATE UNIQUE INDEX accounts_one_equity_per_role
    ON accounts (household_id, equity_role) WHERE equity_role IS NOT NULL;

CREATE TABLE categories (
    id            TEXT PRIMARY KEY,
    household_id  TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    name          TEXT NOT NULL,
    notes         TEXT,
    color         TEXT,                -- palette name (red, orange, amber, lime, green, teal, sky, blue, violet, pink, gray), checked by the service
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    UNIQUE (household_id, name)
) STRICT;

CREATE TABLE tags (
    id            TEXT PRIMARY KEY,
    household_id  TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    name          TEXT NOT NULL,
    description   TEXT,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    UNIQUE (household_id, name)
) STRICT;

CREATE TABLE transaction_groups (
    id                  TEXT PRIMARY KEY,
    household_id        TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    title               TEXT,
    created_by_user_id  TEXT REFERENCES users (id) ON DELETE SET NULL,
    recurrence_id       TEXT,          -- set when generated by a recurrence (FK added in Phase 5)
    recurrence_date     TEXT,
    created_at          TEXT NOT NULL,
    updated_at          TEXT NOT NULL,
    UNIQUE (household_id, id),
    UNIQUE (recurrence_id, recurrence_date)   -- a recurrence fires at most once per date
) STRICT;

CREATE TABLE splits (
    id                      TEXT PRIMARY KEY,
    household_id            TEXT NOT NULL,
    group_id                TEXT NOT NULL,
    position                INTEGER NOT NULL,
    kind                    TEXT NOT NULL CHECK (kind IN ('withdrawal', 'deposit', 'transfer', 'opening_balance', 'reconciliation')),
    date                    TEXT NOT NULL,
    description             TEXT NOT NULL,
    source_account_id       TEXT NOT NULL,
    destination_account_id  TEXT NOT NULL,
    amount_minor            INTEGER NOT NULL CHECK (amount_minor > 0),
    currency_code           TEXT NOT NULL REFERENCES currencies (code),
    foreign_amount_minor    INTEGER CHECK (foreign_amount_minor > 0),
    foreign_currency_code   TEXT REFERENCES currencies (code),
    category_id             TEXT REFERENCES categories (id) ON DELETE SET NULL,
    budget_id               TEXT,      -- FK to budgets added in Phase 5
    bill_id                 TEXT,      -- FK to bills added in Phase 5
    reconciled              INTEGER NOT NULL DEFAULT 0 CHECK (reconciled IN (0, 1)),
    notes                   TEXT,
    meta                    TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(meta)),
    created_at              TEXT NOT NULL,
    updated_at              TEXT NOT NULL,
    UNIQUE (household_id, id),
    UNIQUE (group_id, position),
    FOREIGN KEY (household_id, group_id) REFERENCES transaction_groups (household_id, id) ON DELETE CASCADE,
    FOREIGN KEY (household_id, source_account_id) REFERENCES accounts (household_id, id),
    FOREIGN KEY (household_id, destination_account_id) REFERENCES accounts (household_id, id),
    CHECK (source_account_id <> destination_account_id),
    CHECK ((foreign_amount_minor IS NULL) = (foreign_currency_code IS NULL)),
    CHECK (foreign_currency_code IS NULL OR foreign_currency_code <> currency_code)
) STRICT;
CREATE INDEX splits_household_date ON splits (household_id, date);
CREATE INDEX splits_source_date ON splits (source_account_id, date);
CREATE INDEX splits_destination_date ON splits (destination_account_id, date);
CREATE INDEX splits_category ON splits (category_id);
CREATE INDEX splits_budget ON splits (budget_id);
CREATE INDEX splits_bill ON splits (bill_id);

CREATE TABLE split_tags (
    split_id  TEXT NOT NULL REFERENCES splits (id) ON DELETE CASCADE,
    tag_id    TEXT NOT NULL REFERENCES tags (id) ON DELETE CASCADE,
    PRIMARY KEY (split_id, tag_id)
) STRICT;
CREATE INDEX split_tags_tag ON split_tags (tag_id);

-- File content lives on disk at <data dir>/attachments/<sha256>.
CREATE TABLE attachments (
    id               TEXT PRIMARY KEY,
    household_id     TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    attachable_type  TEXT NOT NULL CHECK (attachable_type IN ('split', 'account', 'bill', 'budget', 'piggy_bank', 'tag')),
    attachable_id    TEXT NOT NULL,
    filename         TEXT NOT NULL,
    title            TEXT,
    mime_type        TEXT NOT NULL,
    size_bytes       INTEGER NOT NULL,
    sha256           TEXT NOT NULL,
    notes            TEXT,
    created_at       TEXT NOT NULL
) STRICT;
CREATE INDEX attachments_target ON attachments (attachable_type, attachable_id);
```

SQLite cannot add a foreign key to an existing column. In Phase 5, `splits.budget_id`, `splits.bill_id` and `transaction_groups.recurrence_id` stay plain columns; the services check that the referenced row exists in the same household, and deleting a budget, bill or recurrence clears the references in the same transaction.

### 5.3 Planning: budgets, bills, piggy banks

```sql
CREATE TABLE budgets (
    id                  TEXT PRIMARY KEY,
    household_id        TEXT NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    name                TEXT NOT NULL,
    active              INTEGER NOT NULL DEFAULT 1 CHECK (active IN (0, 1)),
    sort_order          INTEGER NOT NULL DEFAULT 0,
    notes               TEXT,
    auto_type           TEXT CHECK (auto_type IN ('reset', 'rollover')),   -- only 'reset' is written since Phase 9
    auto_period         TEXT CHECK (auto_period IN ('daily', 'weekly', 'monthly', 'quarterly', 'half_year', 'yearly')),
    auto_amount_minor   INTEGER CHECK (auto_amount_minor > 0),
    auto_currency_code  TEXT REFERENCES currencies (code),
    created_at          TEXT NOT NULL,
    updated_at          TEXT NOT NULL,
```

### 5.4f Credit card plans (Phase 12)

An asset account with `asset_role = 'credit_card'` may have one plan: a monthly budget, the active asset account in the same currency that pays it (`settlement_account_id`) and the day of the following month it is paid (1–31, the last day of a shorter month). A month is a calendar month in household time. A month spent the card's withdrawals minus its deposits (refunds) dated in it, plus those of the month before that were moved to it, minus its own moved to the next; transfers (the payment itself included), opening balances and reconciliations never count. Available = budget − spent. A plan starts with the month it is created in (`starts_cycle`): earlier months get no payment, are not listed and refuse moves.

Budgets are per month: `credit_card_limits` holds each budget with the month it starts; a month's budget is the latest one starting on or before it. New budgets start in the current month or later, so earlier months never change.

The `card-settlements` task (8.5) keeps one payment transfer per month (from the paying account to the card, dated on the settlement day, description `<card> — <Month YYYY>`, origin `scheduler`, rules not run) through the transaction service, so each change appends its `transaction.*` event. A month's state in `credit_card_cycles`: `synced` (the server makes the transfer equal the month's spending until the settlement date; it keeps the owner's category, tags and notes when it updates it), `frozen` (from the settlement date, after a last update, or once the transfer is reconciled: never changed again; later changes show as `difference_after_settlement`), `detached` (the owner edited the amount, date or paying account, reshaped or deleted the transfer: left alone for good). A move is allowed only on a split counting toward the card, when neither its own month nor the next is closed (before `starts_cycle`, frozen, or on/after its settlement date); the exception is a split dated in the month just before `starts_cycle`, which has no budget or payment, so moving it into the plan's first month (and back) only needs that first month open; the task drops moves whose split stopped counting toward the card. Deleting a plan deletes its synced transfers that are not due yet, keeps frozen and detached ones, and removes its budgets, moves and month rows. An account with a plan must stay a credit card in the same currency, and a paying account must stay an active asset account in the same currency and cannot be deleted (409).

### 5.6b Statement import (Phase 13)

Migration `20261127142256_statement_import.sql`.

- **`statement_profiles`**: a household's saved way of reading one bank's export.
  - Columns: `name` (unique per household), an optional default `account_id` (an asset or liability account; `ON DELETE SET NULL`), `format` (`csv`, `xlsx`), and `mapping`, the JSON of `saldo_app::statements::parse::Mapping`.
  - `part_accounts` (JSON): part column header → asset account ID, or null to keep that part as a note (brief decision 13).
  - `transfer_rules` (JSON): `[{ pattern, account_ids }]`.
  - The service checks every account against the household and runs `Mapping::validate()` before saving.
- **`statement_imports`**: one uploaded file.
  - `status` is `draft`, `committed`, `discarded` or `reverted`.
  - It also stores the account's currency, the opening and closing balances, the closing date, and `gap_minor` (opening + lines − closing).
  - `summary` (JSON) holds the counts, the unsupported rows with their reasons, and the findings about existing transactions.
  - Rows that are not transactions live in `summary`, not in `statement_lines`, so the line columns need no NULLs.
- **`statement_lines`**: one importable line, keyed `(import_id, position)`.
  - It keeps the three dates, the signed amount, the bank text, the counterparty fields, the notes and the parts.
  - `ref_key` is the line's identity in `external_refs` (source `bank-statement`, entity `split`): `<account_id>:<external_id>`, or `<account_id>:#<fingerprint>` when the bank gives no ID. Every key starts with the account, so a split linked to one account's statement (a transfer) is still a match candidate for the other account's statement, while one linked to this account's statements is not.
  - `status` and `action`.
  - `split_id`: the matched split, or the first created one.
  - `created_group_id`, for revert.
- **Deleting splits:** deleting a split (with its group, or dropped by a replace) removes its `bank-statement` references in the same transaction (brief decision 11).
- **Origin of created groups:** groups created by a commit carry the caller's origin (`api` from the web app), so the rules run and archived accounts are refused, like hand-made transactions. The import itself is recorded by its own `statement_import.*` events. The events table's `origin` CHECK has no room for a new value without rebuilding the table.

### 5.6c Companion sources (Phase 13)

Migration `20261127172851_sources.sql`.

- **`source_documents`**: one uploaded Amazon or PayPal export (`kind` `amazon_orders` or `paypal`).
  - Unique per household by SHA-256 (the same file twice is a 409).
  - Also stores the file's first and last dates, and how many rows it added and refreshed.
  - The file itself is kept at `<data dir>/sources/<sha256>`. This folder is apart from attachments, which the attachment sweep owns. The file is removed when no household's document names it any more.
- **`source_rows`**: one Amazon item or PayPal row.
  - Unique per household by `(kind, external_id)`: Amazon `order:ASIN:n`, PayPal `Codice transazione`. A newer export therefore adds only new rows and refreshes the known ones.
  - `document_id` and `last_document_id` are the first and latest uploads holding the row. Deleting a document moves a row to the other one, or deletes it when only that upload held it.
  - A delete is refused (409) while such a row explains a committed transaction.
  - Amounts are signed as the source writes them.
  - Amazon rows carry the order ID as `group_key`; `excluded` marks cancelled items and items paid by gift card alone.
- **`source_matches`**: a source row explaining a draft line (`statement_import_id`, `line_position`) or, after commit, a split.
  - Match types: `order_id`, `amount_date`, `approximate`, `funding_pair`, `amount_lag`.
  - A discard or a revert deletes the import's matches, and deleting a split cascades.
- **`statement_lines` gains three columns:**
  - `proposal` (JSON): what the matched source proposes, `{ source, description, counterparty, notes, items: [{ product, amount_minor }] }`;
  - `use_proposal` (default 1);
  - `split_by_item` (default 0).
- **Classification:** rows dated from 30 days before to 3 days after the statement are read, plus every Amazon item of an order ID named in a line.
  - Amazon is matched (`saldo_core::matching::match_amazon`, window −2 to +14 days, no amount tolerance yet) on lines mentioning "amazon" or "amzn".
  - PayPal is matched (`match_paypal`, −2 to +7) on lines mentioning "paypal". PayPal wins on a line both match.
  - A matched order's date is also a candidate date for existing transactions.
- **Commit:** a line keeping its proposal is booked with the proposal's description and counterparty. Its notes start with the bank text, then the source's notes. With `split_by_item`, a single charge becomes one split per item; the difference goes to the largest, and it falls back to one split when it cannot work.

## 6. API

Base path `/api/v1`. JSON only. The OpenAPI document is served at `/api/v1/openapi.json` and written to `web/openapi.json` by `saldo openapi`, so the TypeScript client can be generated without a running server.

Conventions:

- Success: `{ "data": ..., "meta": { "page": 1, "per_page": 50, "total": 1234 } }` (`meta` only on lists). Error: `{ "error": { "code": "validation_failed", "message": "...", "details": [ { "field": "splits[1].amount", "code": "amount_not_positive", "message": "..." } ] } }`.
- Status codes: 200, 201, 204, 400 (malformed), 401, 403, 404, 409 (conflict, e.g. duplicate name), 422 (validation), 429, 500.
- Amounts in JSON are decimal strings plus a currency code: `{ "amount": "12.50", "currency": "EUR" }`. Never JSON numbers.
- Lists take `page`, `per_page` (max 200) and resource filters. Sorting is fixed per resource.
- Every list and report takes `scope=household` (default), `scope=mine`, or `scope=user:<id>`, filtering by account owner.
- A transaction group is always written as a whole: `POST` creates the group with its splits, `PUT` replaces it, `DELETE` removes it. There are no per-split write endpoints. In a `PUT`, a split may carry the `id` of one of the group's splits: that split is updated in place and keeps its ID and attachments; a split without `id` is new; the group's splits that no entry names are deleted with their attachments. An `id` from another group, the same `id` twice, or any `id` in a `POST` is a 422 on `splits[n].id`. Deleting a group or a bill deletes its attachments too (each with `attachment.deleted`).

## 7. Auth and household

- Passwords are hashed with Argon2id. Login is rate-limited per IP and per email.
- Login with an identity provider (Authentik) over OpenID Connect, when `SALDO_OIDC_ISSUER`, `SALDO_OIDC_CLIENT_ID` and `SALDO_OIDC_CLIENT_SECRET` are set: `GET /auth/oidc/start` redirects to the provider (authorization code flow with PKCE; `state` kept in memory for 10 minutes and bound to the browser by an HttpOnly cookie on `/api/v1/auth/oidc`); `GET /auth/oidc/callback` exchanges the code, verifies the ID token (signature from the provider's JWKS, issuer, audience, expiry, nonce) and opens a normal session cookie. The first login links the provider's `sub` to the member whose email matches a verified email (case-insensitive; `SALDO_OIDC_TRUST_EMAIL=true` treats the provider's emails as verified); later logins use the link (`user_identities`). Nobody is created automatically. `SALDO_PASSWORD_LOGIN=false` turns password login off (403). `GET /auth/methods` (public) tells the login page which methods exist.
- The desktop app logs in with the provider through the system browser (RFC 8252 loopback): it listens on a random `127.0.0.1` port, makes a secret verifier and opens `GET /auth/oidc/start?desktop_port=&desktop_challenge=` (S256 of the verifier). After the usual checks the callback keeps the new session under a single-use code (2 minutes, in memory) and redirects to `http://127.0.0.1:<port>/callback?code=…` (or `?error=…`); `POST /auth/oidc/desktop-token { code, verifier }` returns the token once. The token never appears in a URL, and a code is useless without the verifier.
- A login creates a `sessions` row and returns a random 256-bit token. The web app receives it as a cookie `saldo_session` (HttpOnly, SameSite=Lax, and Secure when `SALDO_PUBLIC_URL` is https). The token is never in the login response body. Desktop, scripts and the importer send `Authorization: Bearer <token>`. Personal access tokens are rows of kind `token`, shown once at creation. A login session stores the app it was opened for (`browser` or `desktop`) in `name`, so a member can see where they are logged in and end any of those sessions or all but the current one; sessions and tokens append no events, like login.
- CSRF: a request authenticated by cookie that is not GET/HEAD must carry the header `X-Saldo-Csrf: 1` and an `Origin` matching `SALDO_PUBLIC_URL`. Bearer requests are exempt.
- Every response carries `Content-Security-Policy` (same origin only, no inline scripts, `frame-ancestors 'none'`; `saldo_server::hardening::CONTENT_SECURITY_POLICY`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`, plus `Strict-Transport-Security: max-age=31536000` when `SALDO_PUBLIC_URL` is https. A route may set its own value for any of them. A request whose response is not ready within 120 seconds is answered with 408 (the live-event stream starts its response at once, so it is not cut off).
- CORS is off unless `SALDO_ALLOWED_ORIGINS` lists origins (the desktop app: `tauri://localhost`, `http://tauri.localhost`). Allowed: GET, POST, PUT, PATCH, DELETE with `Authorization`, `Content-Type` and `Last-Event-ID`; never credentials, so cookies stay same-origin.
- The desktop app logs in with `client: "desktop"`, keeps the 30-day session token in the OS keychain and sends it as a bearer token; it reads `GET /events/stream` with `fetch`, since `EventSource` cannot send that header.
- First run: `POST /setup` creates the first user and the household, and only works while the `users` table is empty. The same is available as `saldo user create`.
- An owner adds members with an initial password. v1 has no email invitations and no password-reset email.
- Authorization in v1 is household membership: a member can read and write everything in the household. Owner-only: managing members, webhooks, export and household settings.
- Notification channels are the one exception to "everything is visible to every member": each user sees and manages only their own (owner-approved, Phase 6).
- Every request resolves to a `HouseholdCtx { household_id, user_id, role }`. Every service and repository function takes it as its first parameter and puts `household_id` in every query. Exception (owner-approved, Phase 6): the system tasks that follow one global cursor through the event log (webhook dispatch and delivery, the notification outbox) take no context; every row they write carries its event's household, and they only match endpoints and channels of that household. Also exempt (owner-approved, 2026-11-15): `attachment-sweep`, which compares stored file names (SHA-256) with the `attachments` table across households and reads no household data. There is no way to call a repository without one. (Laravel analogy: a global scope that cannot be removed. Go analogy: a `context.Context` value that is a required typed argument instead of a hidden key.)

## 8. Events, webhooks, notifications

### 8.1 Event log

Every state change is one service method that opens a transaction, validates through `core`, writes the rows, appends one `events` row, and commits. If the event insert fails, the change is rolled back.

Event types are `<entity>.<verb>`:

- CRUD: `account.*`, `transaction.*`, `category.*`, `tag.*`, `budget.*`, `budget_limit.*`, `bill.*`, `piggy_bank.*`, `recurrence.*`, `rule.*`, `rule_group.*`, `household_member.*`, `webhook.*`, `notification_channel.*` (secret-free data), `attachment.*`, `template.*` (transaction templates, Phase 8), `subscription_dismissal.created`/`.deleted` (Phase 9; entity ID `<account_id>:<currency>`), `reconciliation.created`/`.deleted` (Phase 9; setting the splits' flags appends no `transaction.updated`: the reconciliation event lists them), `saved_view.*`, `net_worth_goal.*` (Phase 10), `statement_profile.*` (Phase 13), `source_document.created`/`.deleted` (Phase 13; the document view), each with `created`, `updated`, `deleted`; `statement_import.created`, `.committed`, `.discarded`, `.reverted` (Phase 13; the import without its lines; draft line edits append none), with `import.completed` after a commit (`{ source: "bank-statement", import_id, lines: { create, link, skip } }`); also `household.created` (setup) and `household.updated`.
- `tag.merged`: one per source tag of a merge, with the source as entity and `{ source, into, splits }` as data; it stands for every reference the merge moved (no separate split, recurrence, template or rule events).
- No events (owner-approved): webhook delivery attempts and redelivery, notification rows and their send status (they are outboxes; events would feed back into them), recurrence and consumer cursors, and bill periods created ahead by the scheduler (the bill's own events cover them).
- Setup appends four events in its one transaction: `household.created`, `household_member.created` and two `account.created` (the equity accounts).
- Sessions and API tokens (login, logout, token create/revoke) are authentication state, not household data, and append no event.
- The entity in `data` is the `saldo-app` view type (`AccountView`, `TransactionGroupView`, ...), which is also the API response, so the two cannot drift.
- Domain: `bill.due_soon`, `bill.overdue`, `bill.paid`, `bill.period_skipped`, `bill.period_reopened`, `recurrence.fired` (`{ recurrence_id, date, created, group }`), `piggy_bank.target_reached`, `import.completed`, `webhook.test`. Phase 10 alerts (8.6): `budget.threshold_reached` (`{ budget: { id, name }, limit, threshold, total, alert_key }`), `forecast.below_zero` (`{ account: { id, name }, currency, lowest, alert_key }`), `digest.weekly` (`{ week, currencies, top_categories, bills_due, budgets, alert_key }`), `net_worth_goal.reached` (the goal plus `alert_key`), all with origin `scheduler`; and `transaction.large` (`{ group, split_id, threshold }`), appended with the change for origins `api` and `rule` only, once per split that becomes large (at or above the household's amount in the primary currency). Adding or removing piggy bank money appends `piggy_bank.updated`. Phase 12: `credit_card_plan.created`/`.updated`/`.deleted` (the plan, entity ID the card's account ID; setting a budget is an update) and `credit_card_move.created`/`.deleted` (`{ account_id, split_id, from_cycle, to_cycle }`, entity ID the split), origin `api`, or `scheduler` when the settlement task drops a stale move. Changes made by rules append `transaction.updated` with origin `rule`.

Payload, also the webhook body:

```json
{
  "id": "0193c1a2-...",
  "type": "transaction.created",
  "occurred_at": "2026-11-11T20:21:00.000Z",
  "household_id": "0193...",
  "actor": { "user_id": "0193..." },
  "origin": "api",
  "data": { "...": "the full entity as the API returns it; for deleted, the last state" }
}
```

A `transaction.*` event carries the whole group with all its splits.

### 8.2 Webhook delivery

- A dispatcher task reads events after the `webhooks` cursor, inserts a `webhook_deliveries` row for every active endpoint whose `event_types` match (events with origin `import` only if `include_import_events`), then advances the cursor, all in one transaction.
- A delivery worker picks `pending` rows whose `next_attempt_at` has passed and POSTs the payload with a 10 second timeout and no redirects.
- Headers: `Content-Type: application/json`, `User-Agent: Saldo-Webhook/<version>`, `X-Saldo-Event-Id`, `X-Saldo-Event-Type`, `X-Saldo-Delivery-Id`, `X-Saldo-Signature: t=<unix seconds>,v1=<hex>` where `v1 = HMAC-SHA256(secret, "<t>." + raw body)`. Receivers should reject timestamps older than 5 minutes and compare in constant time.
- Any 2xx is success. Otherwise retry with exponential backoff and 0 to 10% jitter: 1 min, 5 min, 30 min, 2 h, 6 h, 12 h, 24 h; after 8 attempts the delivery is `dead`. An endpoint with 20 consecutive dead deliveries is deactivated with a `disabled_reason` (a `webhook.updated` event with origin `system`).
- An endpoint only receives events that occurred after it was created. `webhook.test` goes only to the endpoint it names, whatever its filter. Pending deliveries of an inactive endpoint wait until it is active again.
- Deliveries are at-least-once and may arrive out of order; receivers deduplicate on `X-Saldo-Event-Id`.
- Private addresses are allowed as targets (Home Assistant, n8n on the LAN are the main use). Only owners manage endpoints; URLs must be `http` or `https`.

### 8.3 Bill reminders

A scheduler task runs at startup and every 15 minutes. For every active bill, using the household's timezone for "today":

1. Create missing `bill_periods` rows from `first_due_date` up to 60 days ahead.
2. For each `open` period, call `core::reminder_due`. If today ≥ `due_date − remind_days_before` and no reminder was sent yet, emit `bill.due_soon`. If today > `due_date` and at least `remind_every_days` have passed since `last_reminded_on`, emit `bill.overdue`. Update `last_reminded_on` and `reminder_count` in the same transaction as the event.

A period becomes `paid` when a split is linked to it: explicitly through `POST /bill-periods/{id}/pay`, or automatically when a split with `bill_id` set is saved: it pays the open period whose due date is nearest to the split's date (`BillSchedule::matching_due_date`). Replacing or deleting the paying group reopens the period. `POST /bill-periods/{id}/skip` and `/reopen` emit `bill.period_skipped` and `bill.period_reopened`. Rules can set `bill_id` with the `link_to_bill` action. Paying emits `bill.paid` and stops reminders.

### 8.4 Notifications

A notifier task reads events after the `notifications` cursor. For each notifying type (`bill.due_soon`, `bill.overdue`, and from Phase 10 `budget.threshold_reached`, `forecast.below_zero`, `transaction.large`, `recurrence.fired`, `piggy_bank.target_reached`, `net_worth_goal.reached`, `digest.weekly`) it inserts one `notifications` row per active channel of every household member whose `event_types` holds the type, with a dedupe key, then sends. `recurrence.fired` notifies only when `created` is true and the origin is `scheduler` (a manual "Fire now" does not). Messages about transactions name the accounts, looked up when the message is built:

- `ntfy` / `gotify`: an HTTP POST to the configured server and topic/token.
- `email`: SMTP, configured by `SALDO_SMTP_*`.
- `webpush`: Web Push with VAPID keys; the channel `config` holds the browser's push subscription.

Failed sends are retried three times (four attempts in all), one attempt per notifier run (every 60 s and after writes), then marked `failed`. A Web Push send that the push service answers with 404 or 410 (the subscription is gone) is not retried: the notification is `failed` at once and the channel is paused (`active = false`, `notification_channel.updated` with origin `system`, in the same transaction). The dedupe key is `<type>:<period id>:<reminder day>` for bill reminders, `<type>:<alert key>` for scheduler alerts, `transaction.large:<split id>`, `recurrence.fired:<recurrence id>:<date>`, else `<type>:<event id>`. Sending is at-least-once: a crash between a send and its bookkeeping sends that one notification again.

### 8.5 Background tasks

All tasks (`webhook-dispatcher`, `webhook-delivery`, `auto-budgets`, `bill-scheduler`, `notifier`, `alert-scheduler` (Phase 10, 8.6), `recurrence-runner`, `card-settlements` (Phase 12, 5.4f: at startup, every 15 minutes and after writes; one database transaction per card, a failing card is logged and retried), `attachment-sweep`) are Tokio tasks started by `saldo serve`, stopped on SIGTERM through a shared cancellation token. Time comes from a `Clock` trait so tests can use a fake clock. Each task must be safe to run again after a crash at any point: all progress is in the database. `attachment-sweep` (at start and hourly) removes stored files that no attachment row uses and that are at least an hour old; deletes only remove rows, inside their database transaction, so a rollback (an importer dry run) never loses a file.

### 8.6 Alerts (Phase 10)

The `alert-scheduler` task runs at startup, every 15 minutes and after writes, for every household (`AlertService::run`, origin `scheduler`), and wakes the notifier when it appended events. Each alert condition has a key; `alert_states` holds the keys that hold now. A key that starts holding is inserted and appends its event in the same transaction; a key that stops holding is deleted (no event), so a later crossing alerts again. Conditions:

- `budget:<limit id>:<80|100>`: a limit of an active budget that contains today has spent at least that share of `amount + carried` (`core::alerts::budget_thresholds`, integer maths; nothing left to spend reaches both as soon as anything is spent).
- `forecast:<account id>`: an active asset account in net worth has a forecast (`/reports/forecast` for that account, 30 days ahead) whose lowest balance is below zero.
- `goal:<goal id>`: a net worth goal reached its target (Phase 10 Track F).
- The weekly digest: from Monday 08:00 household time, once per ISO week (`digest:<year>-W<week>`, only the latest key kept), about the previous Monday to Sunday: cash flow per currency, the three largest expense categories per currency, open bill periods due in the next 7 days (at `amount_max`), and the budgets past 80% today. A household set up mid-week gets that week's digest on the first run.

`alert_states` is bookkeeping: it is not exported and its changes append no events.

## 9. Importer and export

### 9.1 Firefly III importer

`saldo-import firefly --url <firefly url> --token-env <VAR, default FIREFLY_TOKEN> --household <id or name> [--dry-run] [--only accounts,transactions,...] [--since YYYY-MM-DD] [--allow-mismatch]`. The token is read from an environment variable, never an argument. It opens the Saldo database directly (`SALDO_DATABASE_URL`, files under `SALDO_DATA_DIR`) and calls the `saldo-app` services' `<method>_in` variants with origin `import`, all in one database transaction per run (rolled back on `--dry-run`). It only ever sends GET requests to Firefly. It can run while the server is running (WAL mode).

Facts from the Firefly III OpenAPI spec v6.7.8:

- Auth: `Authorization: Bearer <token>`. Lists take `limit` and `page`; the response has `meta.pagination.total_pages`. Default page size is 50.
- Amounts are decimal strings; every object carries `currency_code` and `currency_decimal_places`. Fields prefixed `pc_` are primary-currency conversions and are ignored.
- A transaction is a group (`group_title`, `transactions[]`); each split has `transaction_journal_id`, `type`, `date`, `amount`, `foreign_amount`, `source_id`, `source_type`, `destination_id`, `destination_type`, `category_id`, `budget_id`, `subscription_id` (`bill_id` is the deprecated name), `tags[]` (names), `reconciled`, `notes`, and more.
- Bills are now called subscriptions: use `/v1/subscriptions`.

Import order and mapping:

| # | Firefly endpoint | Saldo | Notes |
|---|---|---|---|
| 1 | `/v1/currencies` | `currencies` | Only enabled ones; fail if `decimal_places` > 8 |
| 2 | `/v1/accounts` | `accounts` | `asset`, `expense`, `revenue`, `liability`/`liabilities` map directly. `initial-balance` → the Equity(OpeningBalance) account; `reconciliation` → Equity(Reconciliation); `cash` → an expense account and a revenue account both named `(cash)`, picked by direction; `import` accounts are skipped and reported. `account_role` `defaultAsset/sharedAsset/savingAsset/ccAsset/cashWalletAsset` → `asset_role`. Opening balances arrive as transactions, not from the account fields |
| 3 | `/v1/categories`, `/v1/tags` | `categories`, `tags` | |
| 4 | `/v1/budgets`, `/v1/budgets/{id}/limits` | `budgets`, `budget_limits` | auto-budget fields map 1:1 (`none` → NULL), except `rollover`: a `reset` auto-budget with carry `leftover`, and its limits in the auto currency above the auto amount import at the auto amount (Firefly stores the leftover in them) |
| 5 | `/v1/subscriptions` | `bills`, `bill_periods` | `date` → `first_due_date`; `paid_dates[]` → paid periods linked to the imported split |
| 6 | `/v1/piggy-banks` | `piggy_banks`, `piggy_bank_accounts` | Linked accounts must be asset accounts. The events come at step 11 |
| 7 | `/v1/rule-groups`, `/v1/rules` | `rule_groups`, `rules`, triggers, actions | Names become IDs and currency labels become codes. Unsupported keywords or unknown names: the rule is imported inactive, keeping the raw values, and listed in the report. Supported triggers and actions are `TRIGGER_KINDS` and `ACTION_KINDS` in `saldo_core::rules` |
| 8 | `/v1/recurrences` | `recurrences`, repetitions, splits | `ndom` → `nth_weekday`; weekend 1-4 → `keep/skip/previous_friday/next_monday`. A new recurrence is marked handled (`fired_through`) up to Firefly's `latest_date` or today, because Firefly already created those transactions |
| 9 | `/v1/transactions` | `transaction_groups`, `splits`, `split_tags` | Paged by date range. Kind is derived by Saldo and compared with Firefly's `type`; a mismatch is reported. SEPA fields, the extra dates, `internal_reference`, `external_url`, `external_id`, `original_source`, `import_hash_v2` and the original date-time go into `meta.firefly` |
| 10 | `/v1/attachments` + download | `attachments` + files | On splits and bills |
| 11 | `/v1/piggy-banks/{id}/events` | `piggy_bank_events` | After transactions, so an event's `transaction_journal_id` resolves to its split |

Rules do not run on imported transactions (origin `import`); a split's Firefly budget link is kept only when the split is a withdrawal in Saldo.

Idempotency: for every object, look up `external_refs (household, 'firefly-iii', entity_type, firefly id)`. If found, update the local row; if not, create it and insert the ref, in one transaction. A split's external ID is its `transaction_journal_id`; a group's is the group ID. Splits that disappeared from a Firefly group are deleted locally on re-import.

Verification, printed at the end of every run and stored in `import_runs.summary`: counts per entity (created / updated / unchanged / skipped), every skipped or downgraded item with the reason, and a balance check comparing each asset and liability account's computed balance with Firefly's `current_balance`.

Checked against the owner's Firefly 6.7.9 in Phase 3; the answers are in `docs/STATUS.md` under "Findings about Firefly III" (notably: transactions are paged by split, list them with `type=all`, amounts carry 12 decimals). Originally unconfirmed: how liability `liability_direction` (`credit`/`debit`) affects signs; the exact shape of piggy bank `accounts[]`; whether `/v1/transaction-links` exposes the link type on read; the maximum `limit`; whether Firefly really forces one shared source or destination per split group (Saldo does not care, but the kind comparison might).

### 9.2 Export

- `GET /api/v1/export/json` and `saldo export json`: one document `{ "format": "saldo-export", "version": 1, "exported_at": ..., "household": ..., "currencies": [...], "accounts": [...], "transactions": [...], ... }` with every table of the household, using the API's own representations. It is complete enough to rebuild the household.
- `GET /api/v1/export/csv` and `saldo export csv`: a zip with one CSV per entity. `transactions.csv` is one row per split with account names, category, budget, bill, tags and decimal amounts, so it opens directly in a spreadsheet; `recurrences.csv` is one row per template split; `templates.csv` (transaction templates, Phase 8) is one row per template split, with account, category, budget, bill and tag names; `subscription_dismissals.csv` (Phase 9) names the account; `reconciliations.csv` (Phase 9) is one row per reconciliation with its number of splits (the JSON export lists them); `saved_views.csv` (Phase 10) has the stored filters as JSON; `net_worth_goals.csv` (Phase 10) has each goal with its net worth on the export day; `credit_card_plans.csv`, `credit_card_limits.csv` (one row per budget and its first month) and `credit_card_moves.csv` (Phase 12); `statement_profiles.csv` (mapping, part accounts and transfer rules as JSON), `source_documents.csv`, `source_rows.csv` and `source_matches.csv` (only matches of booked splits; Phase 13). `credit_card_cycles` is not exported: it is rebuilt by the next run, and the payments are ordinary transactions. Rule triggers and actions read as `kind=value`.
- Left out (owner-approved): the event log, sessions and tokens, `import_runs`, statement imports and their lines (Phase 13: drafts and bookkeeping; what they booked is in the transactions, each split's `meta.statement`, and `source_matches`), the stored source files (their rows are exported), webhook endpoints and deliveries, notification channels and notifications (secrets and bookkeeping, not needed to rebuild the household). Attachment files are referenced by SHA-256, not embedded.
- The SQLite file itself is the third way out: `saldo backup <path>` runs `VACUUM INTO`.

### 9.3 Snapshot and restore

For copying a running instance into a fresh one (tests) without shell access to the server.

- `GET /api/v1/export/snapshot` (owner only): a zip with `saldo.db` (a `VACUUM INTO` copy, deflated) and `attachments/<sha256>` (stored as they are). Only files named by their SHA-256 are taken. The zip is written to a hidden file in `SALDO_DATA_DIR`, whose name is removed before it is streamed; the temporary files are also removed on an error or a cancelled request.
- Unlike the export it is the whole instance, with every household, the event log, password hashes and secrets. So it answers 404 unless `SALDO_SNAPSHOT_DOWNLOAD=true`, and 409 while the instance has a household other than the caller's.
- `saldo restore <zip>`: refuses if the database file of `SALDO_DATABASE_URL` exists, checks every entry first (exactly one `saldo.db`, otherwise only `attachments/<sha256>`, no name twice; anything else writes nothing), writes the files first and the database last, each under a temporary name then linked to its real name (never over an existing database, so a failed restore can run again), runs the migrations, then scrubs the copy (if either fails, the restored database is removed again): deletes sessions and API tokens, webhook endpoints and deliveries, and notification channels and notifications, so the copy cannot reach the original's endpoints or phones. Passwords and identity-provider links stay, so members log in as before. The scrub is maintenance on the whole instance before its first start: it takes no `HouseholdCtx` and appends no events.

## 10. Frontend

| Option | For | Against |
|---|---|---|
| **React + TypeScript SPA (Vite), PWA, Tauri 2 desktop** | One codebase for web, desktop and mobile; typed client generated from OpenAPI; the largest ecosystem (TanStack Query and Router, shadcn/ui, charts); Tauri uses the system webview, roughly a tenth of Electron's memory; the built SPA is embedded in the server binary, so there is still one Docker image | A second language and toolchain; iOS delivers Web Push only to an installed PWA |
| The same with Vue or Svelte | Vue is familiar from Laravel; Svelte has the smallest bundles | Smaller component and chart ecosystems; no decisive gain |
| All-Rust UI (Dioxus, Leptos) | Shares types with `saldo-core`; one language | Doubles the Rust learning load on the hardest part (UI state and lifetimes); few ready-made components; larger WASM payload; mobile is immature |
| t3code style (TS monorepo, Electron, WebSocket RPC) | Proven for realtime-heavy apps | Electron's memory use; an RPC layer is unnecessary for CRUD and reports |
| Flutter, React Native | True native mobile | A third stack; a PWA is enough here |

Chosen: React + TypeScript + Vite, TanStack Query (server state) and TanStack Router, shadcn/ui components on Tailwind, Recharts for charts, `openapi-typescript` + `openapi-fetch` for the generated client, `vite-plugin-pwa` for the service worker.

- `web/src/api/` holds the generated client and is the only code that knows URLs. Its base URL is configurable, because the Tauri app talks to a remote server while the web app uses the same origin.
- The server serves the built SPA from the binary (`rust-embed`) for every path outside `/api`.
- Live updates: the SPA listens to `/api/v1/events/stream` and invalidates the matching queries, so a change made by one household member appears for the other.
- Desktop (Phase 7): a Tauri 2 shell loading the same build, with a first-run screen asking for the server URL, bearer-token auth stored in the OS keychain, and native notifications.
- Desktop updates (after Phase 8): `tauri-plugin-updater` reads `https://github.com/akyrey/saldo/releases/latest/download/latest.json` once at start and on "More > Check for updates", offers a newer version in a banner, downloads and installs it after checking its minisign signature against the public key in `tauri.conf.json`, then restarts (`tauri-plugin-process`). Release tags build signed updater bundles (key in GitHub secrets) and one job writes `latest.json`; drafts are invisible to the updater until published. The web app reaches it through `Platform.checkForUpdate` (`null` in the browser). The repository must be public for the feed to be readable.

## 11. Deployment

- One image built in stages: Node builds `web/`, Rust builds the two binaries (with `cargo-chef` for layer caching), the final stage is a slim Debian image running as a non-root user.
- One volume `/data`: `saldo.db` (plus WAL files) and `attachments/`.
- `docker-compose.yml` with the single service, the volume, a health check on `/healthz`, and an `.env.example`.
- Configuration by environment variables: `SALDO_DATABASE_URL` (default `sqlite:///data/saldo.db`), `SALDO_DATA_DIR`, `SALDO_BIND` (default `0.0.0.0:8080`), `SALDO_PUBLIC_URL`, `SALDO_SMTP_HOST/PORT/TLS/USER/PASSWORD/FROM`, `SALDO_VAPID_PRIVATE_KEY` (from `saldo vapid-keys`) and `SALDO_VAPID_SUBJECT`, `SALDO_ALLOWED_ORIGINS` (CORS, for the desktop app), `SALDO_OIDC_ISSUER/CLIENT_ID/CLIENT_SECRET/NAME/TRUST_EMAIL`, `SALDO_PASSWORD_LOGIN`, `SALDO_SNAPSHOT_DOWNLOAD` (default `false`; 9.3), `SALDO_LOG` (level).
- Images: GitHub Actions (`.github/workflows/docker.yml`) builds amd64 and arm64 natively and publishes one multi-arch tag to Docker Hub (`main`, `sha-…`, and `X.Y.Z`/`X.Y`/`latest` for `vX.Y.Z` tags). The owner's Kubernetes manifests live in their own repository. The server refuses to start with invalid configuration and says which variable is wrong.
- Migrations run at startup. TLS is expected from a reverse proxy.
- Logs are structured (`tracing`), one line per request with a request ID; secrets and tokens are never logged.

## 12. Testing

- Tests are written first. Target: 80% line coverage measured by `cargo llvm-cov`, with `saldo-core` close to 100%.
- `saldo-core`: unit tests next to the code, and `proptest` properties for money arithmetic, kind derivation, ledger balance (sum of all balances is zero) and schedules.
- `saldo-app`: integration tests against an in-memory SQLite database with the real migrations (`#[sqlx::test]`). Every service test also asserts the event row.
- `saldo-server`: API tests that call the Axum router in-process (`tower::ServiceExt::oneshot`), no network. One test asserts that the generated OpenAPI document matches the committed `web/openapi.json`.
- `saldo-importer`: recorded Firefly JSON fixtures served by `wiremock`; one test runs the import twice and asserts that the second run changes nothing.
- Web: Vitest for logic, Playwright for the main flows (login, create a split transaction, see balances).
- CI on every push: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, and from Phase 4 the web lint, type check and tests.
